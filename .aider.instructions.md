# Инструкции по стилю и архитектуре (Go)

### Общие принципы
* **Язык ответов**: Поясняй свои действия на русском языке, комментарии в коде пиши на русском.

### Специфика Go
* **Стандартная библиотека**: Приоритет отдавай стандартной библиотеке Go (standard library), не добавляй новые зависимости без явного разрешения.
* **Обработка ошибок**: Всегда проверяй ошибки (`if err != nil`). Не используй `panic()`, если это не критическая ошибка инициализации.
* **Типизация**: Используй строгую типизацию и интерфейсы там, где это оправдано архитектурно.
* **Документация**: Генерируй комментарии к публичным структурам и методам в стиле Go (начинающиеся с имени функции).
* **Публичный API**: Тщательно подходи к именованию экспортируемых (с большой буквы) функций и структур. Минимизируй количество публичных сущностей, чтобы не раздувать API.
* **Тестирование**: Для каждой новой функции или метода обязательно предлагай тесты в файлах _test.go. Используй стандартный пакет testing.
* **Документация (GoDoc)**: Пиши подробные комментарии для всех экспортируемых элементов, так как они станут официальной документацией библиотеки.
* **Зависимости**: Старайся не добавлять внешние зависимости в go.mod. Если зависимость необходима, обоснуй её выбор.

### Миграция с Perl на Go
* **Идиоматичность**: Не переноси логику Perl один-в-один. Используй структуры данных Go (slices, maps, structs) вместо глобальных хешей и массивов Perl.
* **Регулярные выражения**: В Perl они очень быстрые и встроены в синтаксис. В Go используй пакет `regexp`, но помни, что синтаксис может отличаться (особенно в части Look-ahead/Look-behind).
* **Типизация**: Perl — динамический, Go — статический. При переносе функций всегда определяй четкие структуры (struct) для входных и выходных данных вместо передачи пустых интерфейсов `interface{}`. Насколько это возможно. Обсуждать каждый случай.
* **Строки и Байты**: Внимательно переноси работу со строками. Где в Perl используется обычная строка, в Go часто эффективнее использовать `[]byte` или `strings.Builder`.
* **Режим работы**: Не пиши код для новых функций, пока я явно об этом не попрошу. Твоя основная задача — анализ и пошаговый перенос по моей команде.

### Контекст CommuniGate Pro (PCLI)
* **Протокол**: Библиотека реализует интерфейс к CLI CommuniGate Pro. Основная задача — правильная сериализация данных в формат CLI и парсинг ответов.
* **Документация**: В папке `docs/` лежат HTML-описания API. Всегда сверяй реализацию функций с этими файлами.
* **Типы данных**: Обрати внимание на то, как CLI интерпретирует строки, массивы и словари (dictionaries). В Go они должны быть строго типизированы через структуры.

### Работа с динамическими данными (CGPro CLI)
* **Динамизм**: Учитывай, что ответы CLI могут быть нерегулярными. Не навязывай жесткие структуры (struct) для волатильных данных.
* **Гибкость**: Для сложных ответов предлагай использование `map[string]any` или создание кастомного типа-контейнера, способного безопасно отдавать данные разных типов (Value Object pattern).
* **Парсинг**: При переносе логики из Perl обращай внимание на то, как там обрабатываются вложенные хеши и массивы. В Go это должно быть реализовано через рекурсивный парсер, возвращающий интерфейсы или кастомные типы.

### Безопасность и доступ к файлам
* **СТРОГИЙ ЗАПРЕТ**: Никогда не читай содержимое файла `./env`. В нём содержатся конфиденциальные данные и пароли.
* **Секреты**: Если тебе нужно добавить новую переменную окружения для тестов, проси об этом меня в чате, не пытайся сделать это самостоятельно.

### Тестирование на реальном инстансе
* **Интеграционные тесты**: При создании новых функций для работы с CGP, старайся дополнять их тестами, которые могут быть запущены на живом сервере.
* **Запуск**: Для проверки кода используй команду `/run ./build test`. Если тесты падают, анализируй вывод и исправляй код.

### Тестирование и верификация
* **Тестовый стенд**: Для проверки интеграции используй доступный тестовый инстанс CGP через скрипт `./build test`.
* **Анализ ошибок**: Если запуск тестов через `/run` возвращает ошибку, внимательно анализируй ответ сервера CGP. Возможно, реальный формат данных отличается от описанного в документации.

### Форматирование для Kate/mcedit
* **Целые файлы**: При внесении изменений старайся выдавать код так, чтобы его было удобно вставлять или чтобы `aider` применял его корректно одним блоком.
* **Никаких лишних файлов**: Не создавай новые файлы без предварительного обсуждения, старайся расширять существующую структуру.

### Работа с Git
* **Сообщения коммитов**: Пиши сообщения к коммитам на английском языке в стиле Conventional Commits (например, `feat: add user validation` или `fix: resolve pointer nil dereference`).
